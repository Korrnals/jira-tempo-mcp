## 1. Контекст

Агент-специалист JTM (отчёты Jira/Tempo через MCP-сервер `jira-tempo`) отработал цикл июнь–октябрь 2026; самопроверка специалиста выявила расхождения между документацией агента и фактической tool-схемой сервера, непрописанные правила поведения (fallback на ручную компоновку, поведение при недоступности MCP, семантика рабочей недели) и повторяющиеся ручные операции, закрываемые небольшим набором новых тулз. Документация агента состоит из трёх файлов в `copilot-integration/` (`JTM_AGENT.md`, `jtm-jira-tempo-reports.agent.md`, `jira-tempo-reports.skill.md`); сервер — `src/jira_tempo_mcp/`. Настоящая спецификация переводит фидбек в срезы, контракты с исполняемыми критериями приёмки и протокол верификации «доки = реальность». Решения владельца, действующие без пересмотра, перечислены в §7.

Изменения:

- Строка 6 матрицы (`generate_tasks_report`): фактические параметры — `users`, `active_only`, `format`, `output_dir`; периодов у тулзы **нет** — это снимок текущих задач (tasks_report.py:557–597), а не отчёт за период. Исправить тип и вызов соответственно.
- Пикер (jtm-jira-tempo-reports.agent.md:93–161): Q0-описание, вопросы 3a/3b, все три примера — на `target_date`; вопрос 3b («конец периода») переформулируется (например, «любая дата целевой недели»), пример team-отчёта сохраняет `date_from`/`date_to`.
- Скилл (jira-tempo-reports.skill.md:56): Q0-строка с `date_from=<Mon>, date_to=<Sun>` — на `target_date`.
- Файлы: три файла среза A.
- Acceptance:
  - `grep -n "date_from\|date_to" copilot-integration/JTM_AGENT.md copilot-integration/jtm-jira-tempo-reports.agent.md copilot-integration/jira-tempo-reports.skill.md` — вхождения только в контексте `generate_team_report`;

  - прогон V1 (§4) даёт отчёт за запрошенную прошедшую неделю.

**A2 (P1). Preview-гейт перед ручным fallback + обязательный evidence (§Scenario 4).**
- В §Scenario 4 (JTM_AGENT.md:95–113) добавляется обязательный пре-чек: перед любым ручным fallback вызвать `preview_report_template` ближайшего builtin-шаблона (после среза B3 — в live-режиме с реальными worklogs) и сравнить форму с требованием запроса. Fallback разрешён только при подтверждённом несовпадении формы.
- Fallback-ответ обязан содержать one-line evidence: какой шаблон проверен, чем форма не совпала.
- Acceptance: сценарий содержит шаг гейта и требование evidence; прогон V4.

**A3 (P1). Правило поведения при недоступности MCP.**
- Hard rules (JTM_AGENT.md:190–196) и пикер (agent.md:176–194) дополняются: при недоступности MCP-сервера — сообщить владельцу и остановиться; ручная компоновка из MCP-данных и прямые вызовы запрещены в равной мере. Дополнить §Anti-patterns.
- Acceptance: правило присутствует в обоих файлах; ссылка на раздел диагностики (A8).

**A4 (P1). Семантика `output_dir`/`target_date` + root-containment + конфиг-шаг Komus.**
- §Parameter semantics и §Save paths (JTM_AGENT.md:169–173) приводятся к факту: `output_dir` обязан лежать **внутри** корня `REPORT_OUTPUT_DIR` (fallback при незаданной переменной — `~/.mcp/jira-tempo-mcp/reports/`, config.py:178–181); выход за корень отклоняется защитой от path traversal (server.py:648–675). Следовательно, конвенция Komus (`<Komus>/Отчеты/<ГГГГ>/<месяц>/weekly/`) работает только при `REPORT_OUTPUT_DIR`, указывающем на корень дерева отчётов Komus, — это конфиг-шаг волны (см. §4, пункт «Конфиг»).
- Description тулзы в схеме (server.py:295, «Defaults to REPORT_OUTPUT_DIR env or ./reports») исправляется на фактический fallback (срез B).
- Acceptance: таблица содержит оба параметра с точной семантикой; §Save paths согласован с containment-правилом; неверный путь в прогоне даёт явную ошибку containment (цитата).

**A5 (P1). Секция «Project coupling».**
- Новая секция JTM_AGENT.md: агент — часть проекта `jira-tempo-mcp`; сервер локально сопровождается; builtin-шаблоны кастомизированы под владельца; при сомнении в форме вывода — `preview_report_template` или чтение `src/jira_tempo_mcp/templates/`.
- Acceptance: секция существует, правило зафиксировано.

**A6 (P1). Рабочая неделя пн–пт.**
- Все формулировки Mon–Sun / «Monday of current work week … Sunday» (JTM_AGENT.md:27, 75, 164; agent.md:99, 114–115) приводятся к факту рендера: неделя = пн–пт (_shared.py:16–20, `week_range` → monday/friday).
- Acceptance: `grep -n "Sun\|вс" copilot-integration/JTM_AGENT.md copilot-integration/jtm-jira-tempo-reports.agent.md` — нет формулировок недели, заканчивающейся воскресеньем.

**A7 (P1). §Scenario 5: «текущая задача» и шаблон комментария трекинга.**
- Алгоритм разрешения «текущей задачи»: проектная задача, а не служебный трекер (эвристика `list_user_tasks(status="В работе")` с явной фильтрацией трекеров); при неоднозначности — вопрос владельцу; write (`create_worklog`) — только после подтверждения.

- Acceptance: подраздел существует; примеры проходят стиль-контракт; сценарий 5 прогон end-to-end (V-серия, §4).

**A8 (P1). Раздел «Диагностика подключения» (P6).**

## 4. Протокол верификации (§10 фидбека)

Чек-лист сверки (исполняется по каждому затронутому документу, результат — таблица в отчёте реализации):

1. Инвентарь тулз: каждая тулза из «Tool inventory» существует в схеме (базовое число: 19 = 19 на 2026-10-30; пересчитать после среза B).
2. Параметры: каждый параметр доков есть в схеме и наоборот.
3. Примеры исполняемы «как написаны».
4. Формат отчёта: описание README Komus = фактический вывод генератора.
5. Описания шаблонов: description = фактический рендер.
6. Сценарии 1–6 прогнаны end-to-end от первого вызова до файла/подтверждения.

Прогоны (каждый — с цитатой вывода в отчёте реализации; «доки соответствуют» подтверждается только прогоном):

| # | Прогон | Проверяет |
|---|---|---|
| V1 | Генерация отчёта за **прошедшую** неделю через `target_date` | A1: файл за запрошенную неделю, не за текущую |
| V2 | `preview_report_template` mock + live | B3, A2: форма, отсутствие нового файла |

| V5 | Вызов с неизвестным параметром | B5: явная ошибка |

**Техническое условие live-прогонов:** раннер задаёт `REPORT_OUTPUT_DIR=<временный каталог>` — иначе `_validate_output_dir` (server.py:648–675) отклонит `/tmp`-путь по containment-правилу. Прогон с пользовательским каталогом Komus допустим только при root, покрывающем это дерево.

**Конфиг:** на этапе спецификации `REPORT_OUTPUT_DIR` не обнаружен ни в одном проверенном конфиге харнеса (mcp.json бокса, `.env.local` хоста и бокса, репо-`.env`, настройки zcode — проверка по именам переменных, значения не извлекались). Фактическое значение конфигурации окружения и корня отчётов фиксируется **живым прогоном в волне** — это acceptance конфиг-шага A4/C2 (значение — путь, не секрет; токены при проверке не извлекать).

## 7. Вне scope (решения владельца в силе — не менять без директивы)

- Дублирование заголовка задачи в подпунктах устойчивых секций — «пока оставляем как есть» (2026-10-30); контракты B4/A-серии рендер по умолчанию не меняют.
- `delete_worklog` и корректировка записей — вне scope агента (правка только через Tempo UI).
- Директива «только MCP-тулзы, никаких прямых вызовов» — в силе; усиливается контрактом A3 (запрет ручной компоновки при живом MCP).
- Backlog (не в этой волне): `create_worklogs` пакетный трекинг (неидемпотентен — требует per-entry ответа и запрета авто-ретраев), тулза `report_gaps`, `suggest_current_task`, валидация `weekly_summary`/`team_report`/`by-tasks` против реальных нужд владельца (по мере кейсов).
